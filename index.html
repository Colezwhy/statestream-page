OverviewFigures 1–2

Each prompt needs reasoning about the world and control over generation

Users steer an interactive video while it is being generated. A request can refer to something that happened earlier, can depend on a condition the video has to show first, and should keep its effect until a later prompt replaces it.

Memory lost

“Pick up what was left”

“What was left” points back to an earlier interaction. Without a world state to reason over, the backpack left at 4 s is never brought back.

memory-dependent prompt
Wrong execution

“When the train stops, passengers exit”

The effect has to wait for a trigger. With no visual check, passengers appear while the train is still moving.

conditional prompt
State reversion

“Open the door”, then something else

The door opens, but the conditioning text still describes it as closed, so the next prompt quietly undoes it.

StateStream

Reason over a world state, then control generation

A state program records every requested change, and each new prompt is read against it. Plans are executed step by step and checked on generated frames, and only confirmed results are written into memory.

reason · plan · verify · remember

StateStream reasons over an explicit world state and uses it to control a frozen video generator, with no task-specific training.

A VLM agent turns each prompt into a state update and a step-by-step plan, conditions the generator on the resulting state, and checks generated frames before anything is written into memory.

Changes are carried out at the right time and stay until a later prompt replaces them.

§3 MethodFigures 3–4

Three modules around one shared world state

A VLM agent reasons over the world state and controls a frozen autoregressive video generator (LongLive or Self-Forcing) that renders it. The two share entity names: the same name links a line of the state program, a phrase in the conditioning text, and a region of visual memory.

§3.1

World-State Planning

The State Planner keeps the scene as a small program: named entities, their attributes and locations, and global conditions under world. Each prompt is read against this program, appended as a requested update, and turned into a plan of ordered steps. Every step has an action, the entities it affects, an intended result, a duration, and a yes/no question about one frame. A condition the video must show first becomes a waiting step.

# 3 s · the chest lid opens lid = Part("lid", of=chest) lid.state = "open" verify("Is the chest open?", "yes") # 10 s · a blue fish swims in blue_fish = Creature("bright blue fish", at="near the plants") # 17 s · night light world.light = "deep blue night light" Illustrative state code for the aquarium scene, in the program syntax the planner uses.
§3.2

State-Guided Memory Control

The generator is conditioned on World-State text, which describes every entity as it should now be, plus the description of the step in progress. Its visual memory has three parts: Shared KV anchors the opening scene, Window KV holds recent frames, and Entity KV stores each entity's appearance. Text-Guided KV Extraction finds an entity through cross-attention to its name; Align & Read moves stored keys to where the entity is now and reads them only inside its region.

K̃ₑ = Rot(Δpₑ)·Kₑ , Ṽₑ = Vₑ attention bias b(q,k): Shared KV −βs·D(k) Entity KV γ·Rₑ(q) − βe·(1 − Rₑ(q)) Window KV 0 Rot: relative RoPE shift to the reference time and tracked location. D marks outdated Shared KV during a move or removal; Rₑ marks queries inside entity e's region.
§3.3

Feedback-Guided Execution

The same VLM answers each step's question on generated frames. A confirmed step moves the plan on; a waiting step never times out; an action that runs out of time is marked unverified and its target description stays in the text while later frames are rechecked. Only a confirmed result is written into memory, so memory holds what the video shows rather than what was asked.

B⁺ = (1 − ηᵢMᵢ)⊙B⁻ + ηᵢMᵢ⊙Ĉₜ ηᵢ confirmed or not (1 / 0) Mᵢ region from cross-attention Ĉₜ K/V of the latest block The state program is never rewritten by a check: requested transitions and confirmed outcomes are kept apart.

Locate

Align
Stored keys are rotated by relative RoPE to the reference time of Shared KV and to the entity's tracked location. Values are left unchanged.
Read inside the region
Attention biases raise an entity's reference inside its region and lower it elsewhere, which keeps one copy of the entity. After a departure, the stored entry stays in memory but is marked inactive and receives little attention.

    §4.4 AblationFigure 8

    Each module covers a different failure

    Memory control keeps entities single and present; planning and feedback get the timing right.

    What breaks without each part

    − State-Guided Memory Control
    Fewer interactions succeed, and a single arrival later shows up as several copies, like the second swan.
    − Execution Plans
    The largest drops in success, both overall and for effects that must wait for a trigger.
    − Feedback-Guided Execution
    Fewer changes are visible soon after their prompt, and effects that wait for a trigger succeed less often.
    − Write confirmation
    Writing to memory before a check confirms the result lowers success and adds duplicates.
